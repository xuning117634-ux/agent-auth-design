# 云侧 Agent 安全：授权委托权限控制方案

## 1. 材料目标

本文档用于沉淀方案演讲 PPT 的逐页内容草稿，后续可直接交给 AI 生成 PPT，或继续人工精修为正式演讲材料。

演讲主题：

> 云侧 Agent 安全：授权委托权限控制方案

核心目标：

- 说明云侧 Agent 访问企业系统时，传统身份与权限模型为什么不再充分。
- 拆解 Agent 访问链路中的关键安全问题，包括权限放大、Cookie 透传、缺乏精细化策略、缺乏 A2A 权限传递与审计等。
- 提出一套以 MCP 控制端点、策略控制、授权委托、人在环确认为核心的权限控制方案。
- 用适合方案汇报的方式，让听众快速理解“问题是什么、为什么现在必须解决、方案如何落地”。

目标受众：

- 安全架构、平台架构、AI 平台、IAM/权限系统相关负责人。
- 需要评估 Agent 接入企业内部系统风险与治理方案的技术管理者。
- 需要理解方案边界、建设路径和落地价值的业务与技术决策者。

整体风格：

- 互联网 AI 极简风格。
- 页面留白充足，核心结论突出。
- 少大段文字，多结构化图示、链路图、对比图、权限矩阵。
- 关键词尽量短句化，例如“人授意、Agent 执行、系统可控、过程可审计”。
- 配色建议：深色背景 + 高亮蓝/青/绿色，或浅色背景 + 黑灰文字 + 单一科技高亮色。

## 2. 叙事主线

建议整套材料按照以下逻辑展开：

1. Agent 正在从“辅助工具”变成“可执行主体”。
2. 一旦 Agent 进入企业系统访问链路，传统的人到系统访问模型被打破。
3. 新问题不是“Agent 有没有账号”这么简单，而是“谁授权、授权给谁、能做什么、做到什么程度、出了问题如何追溯”。
4. 必须在 Agent 访问链路中设置可控端点，统一承载审计、策略、授权委托和人在环控制。
5. 方案目标是把 Agent 的能力收进企业可治理边界：最小权限、动态授权、全链路审计、跨 Agent 权限传递可验证。

一句话主张：

> Agent 不能直接继承人的全部权限，而应该通过可审计、可撤销、可约束的授权委托机制获得任务级权限。

## 3. 页面规划草稿

### 第 1 页：背景与趋势 - 大模型的概率性与业务的确定性

页面定位：

- 作为开场页，去掉外部厂商标识，只保留观点框架。
- 用“大模型的不确定性”和“业务系统的确定性要求”形成对比，快速建立安全治理的必要性。
- 不展开技术细节，先让听众理解：Agent 进入业务链路后，权限控制不是增强项，而是基础设施。

核心观点：

- 大模型天然具有概率性，适合理解、生成、规划和辅助决策，但不天然保证每次输出都完全确定。
- 企业业务系统追求的是确定性，尤其关注安全、合规、稳定和可审计。
- 当 Agent 开始代表用户访问系统、调用工具、执行操作时，必须用权限控制机制把“不确定的智能”约束在“确定的业务规则”内。

页面内容草稿：

- 标题：大模型的“概率性” × 业务的“100% 确定性”
- 副标题：左侧：AI 带来的不确定性；右侧：安全必须保证什么
- 关键短句：
  - AI 不是每一步都可预测，业务不能接受关键操作失控
  - Agent 越接近执行链路，越需要权限边界
  - 安全治理的目标：让智能可用、可控、可审计

页面结构建议：

- 左侧模块：AI 的不确定性
  - 幻觉：模型可能生成错误或虚构信息
  - 越权：访问未授权资源
  - 跨域调用：调出权限范围
  - Shadow Agent：未授权 Agent
  - Prompt 注入：恶意指令
- 右侧模块：业务的确定性
  - 可审计：完整操作日志
  - 权责清晰：机制责任主体
  - 0 数据外泄：数据安全
  - 合规可信：满足法规要求
  - 可控：风险可内控
- 底部结论：
  - 没有身份与授权保护的确定边界，AI 永远绕不开安全风险。

- 本页参考图中的外部厂商标识需要在正式 PPT 中删除，仅保留“AI 不确定性 vs 业务确定性”的表达框架。

### 第 2 页：传统访问模型 - 人直接访问系统

页面定位：

- 说明传统访问链路的基本假设。
- 为后面对比 Agent 模式做铺垫。

核心观点：

- 传统模式中，访问主体通常是明确的人或服务账号。
- 权限模型围绕“用户身份、角色、资源、操作”构建。
- 审计链路相对直接：谁在什么时间访问了什么资源，执行了什么操作。

页面内容草稿：

- 标题：传统访问：身份明确，权限边界相对稳定
- 图示建议：
  - 用户 -> SSO/IAM -> 业务系统/API -> 审计日志
- 关键要素：
  - 认证：确认是谁
  - 授权：判断能不能做
  - 审计：记录做了什么

### 第 3 页：Agent 模式 - 人、Agent、工具形成新的访问链路

页面定位：

- 引入 Agent 访问模式，展示链路复杂度上升。
- 参考派拉和周辉乐材料，抽象出统一访问链路。

核心观点：

- Agent 不是简单的 UI，它会规划任务、调用工具、组合多个系统能力。
- 权限判断不能只看用户身份，还要看任务意图、Agent 能力、工具范围和上下文。
- 访问链路从单跳变为多跳：人 -> Agent -> MCP/工具 -> 系统/API。

页面内容草稿：

- 标题：Agent 模式：执行主体被拆分，访问链路被拉长
- 图示建议：
  - 人发起意图 -> Agent 理解/规划 -> MCP 工具调用 -> 企业系统/API -> 返回结果
- 关键变化：
  - 人表达的是“目标”
  - Agent 生成的是“执行计划”
  - 工具执行的是“具体操作”
  - 系统看到的是“调用请求”

待补充材料：

- 派拉材料中 Agent 访问链路相关内容。
- 周辉乐材料中 Agent/MCP/工具调用的架构图或描述。

### 第 4 页：问题总图 - 人想做什么、人能做什么、Agent 能做什么

页面定位：

- 作为问题分析总览页。
- 用三层关系拆解权限失控的根源。

核心观点：

- Agent 安全的关键不只是“用户有没有权限”，而是三个边界必须同时成立：
  - 人想做什么：用户意图是否明确、是否高风险。
  - 人能做什么：用户自身是否具备资源与操作权限。
  - Agent 能做什么：Agent/工具是否被允许代为执行。

页面内容草稿：

- 标题：Agent 权限治理，要同时回答三个问题
- 三个问题：
  - 人想做什么：任务意图与风险识别
  - 人能做什么：用户权限与组织策略
  - Agent 能做什么：委托范围与工具权限
- 页面结论：
  - 只有三者交集内的操作，才应该被允许执行。

图示建议：

- 三个相交圆或三层漏斗：
  - 用户意图
  - 用户权限
  - Agent 委托权限
  - 交集 = 可执行任务权限

### 第 5 页：问题一 - 缺少 MCP 控制端点，链路不可控不可审

页面定位：

- 说明为什么需要 MCP 作为统一控制端点。

核心观点：

- 如果 Agent 直接调用系统 API 或工具，企业很难统一做策略判断和审计。
- MCP 不只是工具协议，也可以成为 Agent 访问企业能力的治理边界。
- 没有统一控制端点，就无法稳定承载权限收敛、调用审计、风险拦截和策略执行。

页面内容草稿：

- 标题：没有控制端点，Agent 调用会绕过企业治理边界
- 风险点：
  - 工具调用分散，审计口径不统一
  - 权限判断散落在各系统，无法统一收敛
  - 高风险操作难以前置拦截
  - 无法形成 Agent 行为画像
- 页面结论：
  - 需要以 MCP/Gateway 作为 Agent 访问企业能力的统一治理入口。

### 第 6 页：问题二 - Cookie 透传导致 Agent 权限过大

页面定位：

- 聚焦 Cookie/Session 透传带来的权限放大问题。

核心观点：

- Cookie 透传本质上是把人的完整登录态交给 Agent。
- Agent 获得的不是任务所需的最小权限，而是用户当前会话下的全部权限。
- 一旦 Agent 规划错误、Prompt 被注入或工具被滥用，风险会按用户权限上限放大。

页面内容草稿：

- 标题：Cookie 透传让 Agent 继承了人的全部权限
- 风险点：
  - 权限过宽：任务只需要读 A，却可操作 B/C/D
  - 不可区分：系统难以区分“人操作”还是“Agent 代操作”
  - 不可约束：无法限制操作次数、时间、资源范围
  - 难追责：审计日志只看到用户身份，看不到委托上下文
- 页面结论：
  - Agent 不应直接复用人的完整会话，而应获得任务级、可约束的委托凭证。

### 第 7 页：问题三 - 缺乏精细化权限策略管控

页面定位：

- 说明传统 RBAC/接口级权限不足以覆盖 Agent 场景。

核心观点：

- Agent 调用需要更细粒度的策略：资源范围、操作类型、数据级别、时间窗口、风险等级、上下文条件。
- 权限控制需要从“能不能调用接口”升级为“在什么条件下、为哪个任务、以什么范围调用”。

页面内容草稿：

- 标题：Agent 需要任务级、上下文感知的权限策略
- 策略维度：
  - 主体：用户、Agent、应用、工具
  - 资源：系统、接口、数据对象、字段
  - 操作：读、写、审批、导出、删除、转发
  - 上下文：任务、时间、地点、设备、风险等级
  - 约束：次数、额度、有效期、审批状态
- 页面结论：
  - 精细化策略是把 Agent 能力安全开放给企业系统的前提。

### 第 8 页：问题四 - 缺乏 A2A 调用权限传递与审计

页面定位：

- 作为 Agent 间协作场景的重点问题页。
- 标记为需要重点完善。

核心观点：

- Agent 之间会出现任务转交、能力协同和跨系统调用。
- A2A 调用中，原始用户意图、授权范围、任务上下文和操作链路容易丢失。
- 如果权限只在第一跳判断，后续 Agent 可能出现越权调用、责任不清和审计断链。

页面内容草稿：

- 标题：A2A 协作让权限传递与责任边界更复杂
- 典型风险：
  - 委托链路断裂：后续 Agent 不知道原始授权范围
  - 权限漂移：子任务权限超过原任务边界
  - 审计断链：只能看到局部调用，看不到完整因果链
  - 责任不清：无法判断是用户授权、Agent 决策还是工具执行导致
- 页面结论：
  - A2A 调用必须携带可验证的授权上下文，并形成跨 Agent 的审计链。

待重点精修：

- A2A 权限传递模型。
- 委托凭证是否支持链式传递、降权传递、不可扩权传递。
- 审计日志如何串联用户意图、Agent 决策、工具调用和系统执行。

### 第 9 页：解决方案总图 - Agent 授权委托权限控制架构

页面定位：

- 从问题转入方案，给出整体架构图。

核心观点：

- 通过统一控制入口承接 Agent 工具调用。
- 通过授权委托机制替代 Cookie 透传。
- 通过策略中心做动态决策。
- 通过审计中心沉淀全链路证据。
- 通过人在环机制处理高风险操作。

页面内容草稿：

- 标题：用授权委托机制，把 Agent 纳入企业权限治理体系
- 架构模块：
  - 用户/业务入口
  - Agent Runtime
  - MCP Gateway / Agent Gateway
  - 授权委托服务
  - 策略中心
  - 风险识别
  - 人在环确认
  - 审计中心
  - 企业系统/API
- 页面结论：
  - Agent 只拿到任务所需的最小权限，所有调用经过统一策略判断和审计。

图示建议：

- 中心放 MCP Gateway。
- 左侧为用户和 Agent。
- 右侧为企业系统/API。
- 下方为策略中心、授权委托、审计中心。
- 高风险链路旁路到人在环确认。

### 第 10 页：策略控制 - 从静态权限到动态决策

页面定位：

- 展开“策略控制”这一方案能力。

核心观点：

- 策略控制需要同时评估用户权限、Agent 权限、任务上下文和风险信号。
- 决策结果不只是允许/拒绝，还包括降权、脱敏、二次确认、限流、记录增强审计等。

页面内容草稿：

- 标题：策略控制：每一次 Agent 调用都应被动态评估
- 输入：
  - 用户身份与角色
  - Agent 身份与可信等级
  - 工具/API 类型
  - 资源与数据范围
  - 任务意图
  - 风险上下文
- 输出：
  - Allow：允许
  - Deny：拒绝
  - Step-up：提升认证或二次确认
  - Scope-down：缩小权限范围
  - Mask：数据脱敏
  - Audit：增强审计
- 页面结论：
  - 策略中心让 Agent 权限从“继承用户权限”变为“按任务动态授予”。

### 第 11 页：人在环 - 高风险操作必须回到人确认

页面定位：

- 展开“人在环”机制，突出安全与体验平衡。

核心观点：

- 不是所有 Agent 操作都需要人工确认。
- 对高风险、不可逆、敏感数据、跨边界转发等操作，需要人在环确认。
- 人在环确认不是弹窗，而是把用户意图、操作影响和授权范围结构化呈现。

页面内容草稿：

- 标题：人在环：让关键授权重新回到用户手中
- 触发场景：
  - 删除、转账、审批、发布、外发
  - 批量导出敏感数据
  - 权限变更或账号操作
  - A2A 跨边界委托
  - 风险评分超过阈值
- 确认内容：
  - Agent 准备做什么
  - 涉及哪些资源和数据
  - 权限有效期和范围
  - 操作风险与影响
- 页面结论：
  - 人在环不是降低自动化，而是给高风险自动化加上可解释的安全阀。

### 第 12 页：阶段性建设路径

页面定位：

- 可选收尾页，给出落地节奏。

核心观点：

- Agent 权限治理可分阶段建设，不必一次性完成所有能力。
- 先收口链路，再替换 Cookie，再做精细化策略，最后完善 A2A 与生态治理。

页面内容草稿：

- 标题：从链路收口到生态治理，分阶段落地 Agent 安全
- 阶段 1：接入收口
  - 建设 MCP/Agent Gateway
  - 统一工具接入、日志与审计
- 阶段 2：授权委托
  - 替换 Cookie 透传
  - 引入任务级委托凭证
- 阶段 3：策略控制
  - 接入策略中心
  - 支持动态授权、降权、脱敏、二次确认
- 阶段 4：A2A 治理
  - 支持链式授权上下文
  - 完成跨 Agent 审计与责任追踪

## 5. 建议的演讲节奏

- 背景与趋势：2-3 页，约 5 分钟。
- 问题拆解：5 页，约 10-12 分钟。
- 解决方案：3 页，约 8-10 分钟。
- 建设路径与总结：1 页，约 3 分钟。

总时长建议：

- 精简汇报版：15 分钟，保留 8-9 页。
- 完整方案版：25-30 分钟，保留 11-12 页。
