# Agent 安全方案背景说明书

> 阅读对象：项目负责人、业务负责人、Agent 项目接入方。

> 配套图片：![Agent 安全委托授权架构图](../99-assets/agent-auth-mcp-architecture.png)

## 1. 项目背景

本项目是公司级 Agent 安全委托授权项目，主要服务于公司内部 Agent 项目，例如财经 Eureka X 等云侧 Agent 场景。

当前很多 Agent 的使用方式是：用户先通过 Web 后端与 Agent 对话，Agent 再调用 MCP 工具访问企业内部系统并完成任务。这个模式可以提升效率，但也带来了新的安全问题：Agent 不再只是“回答问题”，而是开始代表用户访问系统、调用接口、执行动作。

因此，项目的核心目标是建设一套统一的 Agent 安全委托授权机制，让 Agent 在帮助用户完成任务时，既能顺畅调用工具，又不能绕过用户授权和公司权限边界。

## 2. 当前主要问题

### 问题一：Cookie 直接透传，Agent 权限过大

用户通过 IDaaS SSO 登录后，业务系统会持有用户 Cookie。传统做法可能把 Cookie 直接透传给 Agent，让 Agent 再拿 Cookie 调用后端接口。

这种方式风险较大：

- Agent 拿到的是用户完整登录态，而不是被限制过的授权凭证。
- Agent 一旦异常调用工具，可能越过用户真实意图访问更多能力。
- 用户无法清楚控制 Agent 到底可以做什么、不可以做什么。

本方案要把 Cookie 从 Agent 手里收回来，由 Agent 网关隔离保存。Agent 只拿临时 token，不能直接接触 Cookie。

### 问题二：缺少精细化委托控制

Agent 执行任务时，可能会涉及查询、创建、修改、删除等不同风险等级的操作。如果没有统一委托机制，用户很难做到：

- 指定某个 Agent 只能调用哪些工具。
- 限制 Agent 能访问的数据范围。
- 在高风险动作发生前进行确认。

本方案通过权限策略中心统一管理 Agent、工具和授权策略。Agent 调工具前，必须经过策略中心判断是否允许。

### 问题三：A2A 调用时权限传递不清楚

未来 Agent 之间会互相协作。例如 AgentA 接到用户任务后，可能调用 AgentB 完成其中一部分工作。

如果没有 A2A 授权机制，就会出现几个问题：

- AgentA 调 AgentB 时，用户授权关系如何传递不清楚。
- AgentB 调工具时，到底继承谁的权限不清楚。
- 多个 Agent 协作后，审计时很难还原是谁代表用户调用了什么工具。

本方案要求 A2A 调用必须经过 Agent 网关，Agent 网关负责 token 换取和上下文记录，策略中心负责判断当前 Agent 协作链路是否允许访问目标工具。

## 3. 方案目标

本项目希望解决四类核心问题：

| 目标 | 说明 |
| --- | --- |
| Cookie 安全转换 | 用户 Cookie 不再直接给 Agent，而是由 Agent 网关隔离保存，并换成临时 token 给 Agent 使用。 |
| 精细化委托控制 | 用户和管理员可以控制 Agent 能调用哪些工具、能访问哪些数据范围。 |
| A2A 权限传递 | Agent 调 Agent 时，通过 Agent 网关完成 token 换取和上下文记录，避免权限链路失控。 |
| 实时确认机制 | Agent 调用敏感工具时，如果当前对话未授权，需要触发用户确认后才能继续。 |

简单来说，本方案不是阻止 Agent 调工具，而是让 Agent 调工具变得“可授权、可控制、可审计、可追责”。

## 4. 架构图怎么看

架构图分成两个阶段：

```text
阶段一：用户登录与 Agent 换证
阶段二：MCP 调用与动态授权
```

### 阶段一：用户登录与 Agent 换证

这一阶段解决的是：用户登录后，如何让 Agent 获得“可控的临时身份”，而不是直接拿到用户 Cookie。

主要流程如下：

1. 用户访问业务系统或智能体入口。
2. 用户通过 IDaaS 完成登录。
3. 业务后端向 Agent 网关发起请求，并带上用户身份、对话信息和 Cookie。
4. Agent 网关通过 IAM 校验应用身份。
5. Agent 网关隔离保存 Cookie，并生成临时 token 给 Agent。
6. Agent 后续只使用 token 执行任务，不直接接触 Cookie。

这一阶段的关键价值是：**把用户原始登录态从 Agent 中隔离出来，用受控 token 代替 Cookie 透传。**

### 阶段二：MCP 调用与动态授权

这一阶段解决的是：Agent 想调用某个 MCP 工具时，系统如何判断能不能放行。

主要流程如下：

1. Agent 携带 token 调用 MCP 网关。
2. MCP 网关把 token 和目标工具信息提交给权限策略中心。
3. 权限策略中心根据 Agent、用户、对话、工具和策略配置进行判断。
4. 如果允许，MCP 网关再向 Agent 网关换取对应 Cookie。
5. MCP 网关注入 Cookie 后调用 MCP Server。
6. MCP Server 最终访问企业业务 API。

这一阶段的关键价值是：**工具调用不是 Agent 想调就调，而是每次经过策略中心动态授权。**

## 5. 各模块在方案中的作用

| 模块 | 作用 |
| --- | --- |
| 业务后端 | 承接用户请求和业务会话，负责触发用户授权确认页面。 |
| IDaaS | 负责用户登录和 SSO 身份认证。 |
| IAM | 负责应用身份认证，确认业务后端、网关等系统身份可信。 |
| Agent 网关 | 负责 Agent 接入、token 生成、Cookie 隔离保存、Agent 路由和 A2A token 换取。 |
| Agent | 执行用户任务，使用 token 调 MCP 工具，不直接接触 Cookie。 |
| MCP 网关 | 负责工具调用入口，调用策略中心做授权判断，允许后完成 Cookie 还原与注入。 |
| 权限策略中心 | 管理工具/Agent 标签、委托关系、授权策略和审计，是动态授权决策核心。 |
| MCP Server | 承接具体工具实现，最终调用企业内部业务 API。 |

## 6. 用户授权是怎么发生的

当 Agent 调用一个需要授权的工具时，如果当前对话还没有授权记录，系统不会直接放行。

这时流程是：

1. MCP 网关向策略中心查询授权。
2. 策略中心发现当前对话未授权，返回拒绝或待授权状态。
3. Agent 保存当前任务进度，进入等待状态。
4. 业务后端触发用户授权确认页面。
5. 用户确认后，策略中心写入本次对话授权记录。
6. Agent 恢复任务，重新发起工具调用。

这就是“人在回路”的授权机制。它保证敏感动作发生前，用户有机会明确确认。

## 7. A2A 场景怎么控制权限

A2A 是指 Agent 调用 Agent。例如用户把任务交给 AgentA，AgentA 又调用 AgentB 完成其中一部分任务。

本方案对 A2A 的控制原则是：

- AgentA 不能直接访问 AgentB，必须经过 Agent 网关（A2A）。
- Agent 网关（A2A）为 AgentB 换取自己的临时 token。
- AgentB 调 MCP 工具时，仍然要走 MCP 网关和策略中心。
- 策略中心会结合 A2A 配置、当前 token、目标工具和用户本次对话授权一起判断。
- 审计日志需要记录 AgentA、AgentB、用户、对话和工具调用关系。

这样做的结果是：即使多个 Agent 协作，也能知道“谁代表谁、在什么对话里、调用了什么工具、是否经过授权”。

## 8. 方案带来的价值

### 对安全侧

- 避免 Cookie 直接暴露给 Agent。
- 避免 Agent 越权调用工具。
- 高风险工具调用可以要求用户实时确认。
- A2A 调用链路可审计、可追溯。

### 对业务侧

- Agent 仍然可以调用现有 MCP 工具和业务 API。
- 业务系统不需要为每个 Agent 单独设计一套安全机制。
- 新 Agent 接入时，可以复用统一网关和策略中心能力。
- 后续扩展到更多 Agent 协作场景时，权限边界更清晰。

### 对平台侧

- Agent 网关统一管理 token、Cookie 和 Agent 接入。
- 策略中心统一管理工具授权、委托关系和策略审计。
- MCP 网关统一执行工具调用前的授权检查。
- 整体架构可以沉淀为公司级 Agent 安全基础能力。

## 9. 一句话总结

本方案的核心是：**用户身份与 Agent 身份联合认证，Cookie 不给 Agent，工具调用必须动态授权，敏感操作需要用户确认，A2A 协作必须经过网关和策略中心约束。**

通过这套机制，Agent 可以安全地代表用户完成任务，但不能脱离用户授权和公司策略边界自由调用工具。
