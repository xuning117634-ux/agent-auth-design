# 公司补充背景

## 1. 项目定位

本项目是公司级 Agent 安全委托授权项目，主要服务于公司内部的 Agent 项目，例如财经 Eureka X 等云侧 Agent 场景。
当前系统中，用户通过Web后端与Agent进行人机交互，Agent调用MCP工具执行任务。现有机制存在以下问题。

**问题1：Cookie透传导致权限过大**
- 用户通过IDaaS SSO登录后，Cookie直接透传到Agent
- Agent拥有用户的全部权限，可能滥用权限执行未授权操作
- 用户无法限制Agent的权限范围

**问题2：委托机制缺失**
- 用户无法精细控制Agent可执行的操作
- 用户无法限制Agent可访问的数据范围
- Agent执行敏感操作时，无用户确认机制

**问题3：A2A调用权限传递问题**
- Agent调用Agent（A2A模式）时，权限传递机制不清晰
- 委托关系在A2A调用链中如何传递未定义
- 权限范围在A2A调用中如何限定未明确
设计一个安全的Agent人机委托机制，解决上述问题：

- **Cookie安全转换**：将Cookie转换为临时Token，避免Cookie透传
- **精细化委托控制**：用户可配置Agent的权限范围和数据范围
- **A2A权限传递**：支持Agent调用Agent的委托链传递
- **实时确认机制**：高危操作强制用户实时确认
---

## 2. 内外网协作背景

公司内网环境不能访问 ChatGPT，只能使用公司内已有 AI 开发工具。目前公司内 AI 工具使用的模型主要是 GLM-5，模型能力相对有限，适合做初步头脑风暴和辅助生成，但不足以支撑完整、严肃、可落地的 Agent 安全架构设计。

因此，本项目采用内网与外网协作开发模式：

- 公司内网负责接触真实业务背景、内部系统、公司已有网关与鉴权能力、架构图和约束信息。
- 外网借助 ChatGPT 的更强推理与设计能力，协助完成 Agent 委托授权安全方案的梳理、补强、重构和开发落地。
- 外网协作材料应避免包含敏感生产数据、密钥、真实用户隐私、内部不可外传接口细节等内容。

该协作模式的目的不是让外网直接替代公司内实现，而是借助更强模型能力，把初版想法整理成可以在公司内落地开发的安全设计、接口边界和实现任务。

## 3. 公司已有基础设施

公司内部已经存在以下基础设施和服务：

- SSO 单点登录服务：IDaaS 服务，负责用户登录与用户身份认证。
- 鉴权服务：IAM 服务，负责应用身份认证、权限校验等鉴权能力。
- 应用负载均衡：ALB。
- Agent 网关初始版本：已有初始能力，支持 A2A 协议通信。
- MCP 网关初始版本：已有初始能力，支持工具注册及工具调用。

这些已有能力是本项目设计的基础约束。后续设计不应重复建设 IDaaS、IAM、ALB、MCP 网关已有通用能力，而应明确复用方式、调用边界和需要补充改造的点。

## 4. 当前建设目标与责任边界

当前主要建设目标是 Agent 网关和策略中心。

其中：

- Agent 网关是当前需要重点负责建设的服务之一，主要涉及 Token 生成与管理、Cookie 换取、Agent 注册管理、Agent 入口代理、A2A 调用链路中的身份与委托信息传递等。
- 策略中心是当前需要重点负责建设的服务之一，主要涉及工具/Agent 标签管理、委托关系管理、权限决策引擎、策略审计、人在环确认相关策略等。
- MCP 网关由同事负责实现。涉及 MCP 网关需要配合改动的点，需要在设计中明确说明并知会相关同事，但不需要本人直接实现 MCP 网关代码。

后续设计文档需要清晰区分：

- 本项目必须实现的 Agent 网关能力。
- 本项目必须实现的策略中心能力。
- MCP 网关需要配合改造的接口、协议、鉴权调用或调用链上下文传递能力。
- IDaaS、IAM、ALB 等公司已有系统需要复用或对接的能力。


## 5. 当前协作目标

当前阶段的主要目标是：

1. 基于公司真实背景和已有初版材料，重新梳理 Agent 委托授权安全架构。
2. 明确 Agent 网关、策略中心、MCP 网关、IDaaS、IAM、业务后端、Agent、MCP Server 之间的职责边界。
3. 补全威胁模型、信任边界、Token 模型、委托策略模型、人在环确认模型和审计模型。
4. 将初版设计材料重构为可评审、可拆解、可开发、可验收的正式设计文档。
5. 在设计明确后，进入 Agent 网关和策略中心的代码开发。
